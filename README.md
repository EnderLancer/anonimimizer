# Псевдонімізація українських судових рішень

Гібридне рішення: NER-модель + правила (regex) для ОСОБА, НОМЕР / ІНФОРМАЦІЯ / АДРЕСА.

## Запуск

```bash
python run.py cases.jsonl out.jsonl --mode model         # 0. лише NER-модель (ОСОБА), без правил
python run.py cases.jsonl out.jsonl --mode regex         # 1. лише правила
python run.py cases.jsonl out.jsonl --mode model_regex   # 2. NER-модель + правила (за замовчуванням, найкраще)
```

Оцінка: офіційним `evaluate.py` організаторів: `python data/evaluate.py data/test/court_cases.jsonl results/model_regex.jsonl`. CI (`.github/workflows/evaluate.yml`) на кожен PR і push у main проганяє всі три режими на тесті й пише результат у summary.

### Повний deanonymization risk

`evaluate.py` рахує ризик лише за іменами: особа розкрита, якщо не приховано хоч одну згадку її ПІБ. Завдання з зірочкою вимагає повну версію: особа захищена, лише якщо псевдонімізовано всі згадки імені **і** всі дати, номери й адреси саме цієї особи. Готової розмітки «особа → її дані» немає, тому ми її побудували:

- `data/test/person_links.json` — для кожного псевдоніма НОМЕР / АДРЕСА / ІНФОРМАЦІЯ в тесті: власники (`owners`, список ОСОБА_n, може бути порожнім або з кількох осіб) і вид даних (`kind`: rnokpp, passport, dob, military_unit, property_address …). Зв'язки розмітив Claude Opus 5.5 (агенти Claude Code, по 12 документів на агента) за текстом реєстру `pseudonymized`, де замість даних стоять плейсхолдери: реальних ПІБ модель не бачила, а відповідь прив'язана до псевдоніма, а не до позиції в тексті. Правила розмітки — в `data/link_persons.py` (`SYSTEM`): реквізити поруч з іменем належать цій особі, номер чи назва військової частини — військовослужбовцю, про якого справа, майно юрособи, адреса суду, номери проваджень — нічиї. З 375 псевдонімів даних 317 мають власника (АДРЕСА 117/125, ІНФОРМАЦІЯ 89/95, НОМЕР 111/155, решта НОМЕР — переважно військові частини без фізособи), 71 — кількох. Перебудувати: `python data/link_persons.py --export tasks/` → відповіді агентів `answers/<id>.json` → `--import answers/`; той самий скрипт уміє питати API (`ANTHROPIC_API_KEY`) і порівнювати файл з евристикою за відстанню (`--check`).
- `data/evaluate_risk.py` — сама метрика, лише stdlib: `python data/evaluate_risk.py data/test/court_cases.jsonl results/model_regex.jsonl [--json] [--details]`. Особа розкрита, якщо не приховано хоч одну згадку імені або хоч одну згадку будь-якого псевдоніма даних, власником якого вона є. Згадку приховано, якщо в кожному буквено-цифровому токені замасковано ≥50% символів — правило `evaluate.py`, але з токенами з цифр (`WORD` в `evaluate.py` не бачить «7955136227» і вважав би номер прихованим). Ризик за іменами звіт показує окремо і він збігається з `evaluate.py`. `--details` перелічує кожну відкриту згадку з власником і видом даних. CI рахує метрику в обох workflow (`out/risk.json` в артефакті, колонка «Ризик повний» у таблиці NER-моделей).

| Режим | Ризик за іменами (`evaluate.py`) | Ризик повний | з них лише через дані | Відкриті дані |
|---|---|---|---|---|
| 0 `model` | .086 | **.405** | 275 осіб | в/ч 354, адреси майна 173, дати 79 |
| 1 `regex` | .057 | .118 | 53 | адреси майна 25, дати 17 |
| 2 `model_regex` | .056 | **.123** | 58 | адреси майна 25, дати 16 |

Сама NER-модель (режим 0) без правил розкриває 40% осіб: вона не маскує номери, адреси й дати. Правила закривають майже все; у найкращому режимі лишаються переважно адреси майна і дати (`--details` показує кожну таку згадку). Прибраний режим з CRF давав повний ризик .106 (43 особи лише через дані).

Для режимів 0 і 2 потрібна модель `uk_ner_web_trf_13class` (spaCy): покладіть її в `models/uk_ner_web_trf_13class` або задайте шлях змінною `UK_NER_MODEL`. Вихід моделі для тесту вже збережено в `ner_cache.json`, тому на тесті інференс не запускається.

### Інші NER-моделі (Hugging Face)

Модель для ОСОБА (і, за бажанням, інших типів) задається через `--ner`. Адаптери в `ner_adapters.py` зводять будь-який вихід моделі до одного формату `EntitySpan(start, end, text, label, score)` (позиції символів у документі), з яким працює решта пайплайну.

```bash
python run.py cases.jsonl out.jsonl --ner "hf:dslim/bert-base-NER?aggregation=first&min_score=0.6"
python run.py cases.jsonl out.jsonl --ner "gliner:urchade/gliner_multi-v2.1?labels=person,address&threshold=0.4" --ner-label ADDRESS=АДРЕСА
python run.py cases.jsonl out.jsonl --ner spacy:path/to/model   # за замовчуванням: spaCy-модель з UK_NER_MODEL
```

| Тип | Формат виходу моделі | Опції (`?ключ=значення&…`) | Пакет |
|---|---|---|---|
| `spacy` | `doc.ents` | `batch_size` | `spacy` |
| `hf` | `transformers.pipeline("token-classification")`: з агрегацією (`entity_group`) і без (`B-PER`/`I-PER` по токенах); позиції або, якщо їх немає, пошук за `word` | `aggregation`, `min_score`, `device`, `max_chars`, `overlap`, `batch_size`, `join_spaces`, `trust_remote_code` | `transformers`, `torch` |
| `gliner` | `predict_entities` → `{start, end, label, score}` | `labels`, `threshold`, `device`, `max_chars`, `overlap`, `join_spaces` | `gliner` |

- Мітки моделі переводяться в типи челенджу через `--ner-label МІТКА=ТИП` (повторюваний). Мітки, що вже є типами челенджу (`ОСОБА`, `АДРЕСА`, `НОМЕР`, `ІНФОРМАЦІЯ` — так розмічають моделі з `train/`), ідуть як є. За замовчуванням у ОСОБА йдуть `PER`, `PERS`, `PERSON` і частини імені з PII-моделей (`GIVEN_NAME`, `SURNAME`, `FIRST_NAME`, `LAST_NAME`, `NAME`…), решта відкидається; `МІТКА=` вимикає мітку. Не-ОСОБА фрагменти моделі йдуть у пайплайн як додаткові кандидати поруч із правилами.
- `--ner-label @pii` вмикає набір міток PII-моделей: адреси, номери (паспорт, ІПН, IBAN, телефон, номерний знак…), дату народження, email. Тип із зірочкою (`CITY=АДРЕСА*`) — «слабка» частина: місто чи область лишаються лише в складі адреси з вулицею.
- **Складання частин** (`ner_postprocess.py`, окремий крок після адаптера). PII-моделі повертають сутність шматками: «Олена» + «Соловей», або вулиця, «14», «м. Кропивницький», «Кіровоградська область» окремо. Частини одного типу, що перетинаються або розділені пробілом (для адрес — ще «, буд.», «, кв.», «, м.»…), складаються в одну сутність, бо окремі шматки не дотягують до IoU 0,5 з розміткою.
- Результат `Wismut/nym-pii-multilingual` на тесті (заміряно ще з CRF у режимі з правилами): лише імена — `model` .237, з правилами .912; з `@pii` — `model` .641 (АДРЕСА .833), але з правилами .815. Номери моделі здебільшого неособисті (реєстрові, договорів, коди бюджету), а розмітка челенджу таких не маскує, тож разом з правилами вони шкодять (НОМЕР .972 → .626). Тому `@pii` вимкнено за замовчуванням.
- Адаптер прибирає BIO-префікси, розширює фрагменти до меж слів (субтокени), склеює фрагменти однієї мітки, між якими лише пробіл (`join_spaces=0` вимикає), і ріже довгі документи на вікна з перекриттям, що вміщаються в модель.
- Кеш окремий для кожної моделі: `ner_cache/<модель>.json` (для моделі за замовчуванням — `ner_cache.json`). У кеші лежать сирі мітки, тож `--ner-label` можна змінювати без повторного інференсу.
- Новий формат: клас з методом `predict_one(text) -> list[EntitySpan]` (зручно через `normalize()`), зареєстрований декоратором `@register("тип")`.
- Ще опція `revision` (гілка, тег або коміт моделі на HF) для `hf` і `gliner`.
- `trust_remote_code=1` (`hf`) виконує код з репозиторію моделі. Потрібна для `davidmelash/modern_liberta_*`: їхній токенізатор LiBERTa лежить у репозиторії, напр. `--ner "hf:davidmelash/modern_liberta_large_w2048_v7_2026-10-09_r5_s43?trust_remote_code=1"`.
- `hf` з fast-токенізатором ріже документ на вікна по токенах (до ліміту моделі, перекриття `stride`, за замовчуванням 64 токени). Для моделей з англомовним словником кирилиця йде майже по токену на символ, тож вікна по символах були б або задовгими, або напівпорожніми. `quantize=1` вмикає динамічну int8-квантизацію: на CPU швидше в ~1,5–2 рази, точність може трохи змінитися.
- **Приватні моделі:** токен Hugging Face береться зі змінної середовища `HF_TOKEN`. У рядок моделі його не пишемо: рядок потрапляє в логи й у назву кешу.

#### Запуск у GitHub Actions

Actions → **NER model evaluation** → Run workflow (`.github/workflows/ner-models.yml`, лише ручний запуск). Інференс іде на CPU і ділиться на `shards` паралельних jobs (за замовчуванням 8, частини збалансовані за довжиною тексту). Job `merge` зливає частини в `ner_cache/` і кешує результат між запусками: та сама модель з тими самими опціями на тих самих даних більше не проганяється, тож зміна `ner_labels` чи `modes` займає хвилини. Далі кожен режим оцінюється окремо, а job `summary` збирає таблицю балів за режимами.

Локально те саме: `python ner_adapters.py infer data.jsonl --ner SPEC --shard 0/4 --out part0.json`, потім `python ner_adapters.py merge data.jsonl --ner SPEC part*.json`.

Параметри запуску:

| Параметр | Що задає |
|---|---|
| `scenario` | готовий набір налаштувань, див. нижче |
| `model_type`, `model` | тип адаптера (`hf` / `gliner` / `spacy`) і репозиторій або пакет |
| `ner_labels` | `МІТКА=ТИП` через пробіл, як `--ner-label` |
| `ner_options` | опції адаптера: `revision=v2&aggregation=first&min_score=0.6`, для GLiNER `labels=person,address&threshold=0.4` |
| `overrides` | перекрити сценарій: `limit=50 shards=4 modes=model,model_regex fail_below=85 data=… cosine=1 cosine_model=… extra_pip="…"` |

| Сценарій | Режими | Jobs інференсу | Інше |
|---|---|---|---|
| `standard` | model, model_regex | 8 | весь тест |
| `quick` | model, model_regex | 2 | 20 документів: чи модель узагалі працює |
| `compare` | regex, model, model_regex | 8 | `regex` як базова лінія без моделі |
| `fast` | model, model_regex | 16 | int8-квантизація (`quantize=1`, лише `hf`) |
| `thorough` | regex, model, model_regex | 8 | + cosine similarity |

Сценарії описані в `.github/scripts/resolve_run.py` (`SCENARIOS`). Порожня опція моделі означає значення адаптера за замовчуванням. Невідома для типу моделі опція в `ner_options` дає помилку ще до запуску інференсу.

Для приватних моделей додайте секрет репозиторію `HF_TOKEN` (Settings → Secrets and variables → Actions) з read-токеном спільного акаунта Hugging Face. Токен передається лише в job `ner`.

### Демо (Hugging Face Space)

`space/app.py` — Gradio-демо: текст рішення ──► режим (0–2) ──► підсвічені сутності, псевдонімізований текст і анотації. NER-модель задається в інтерфейсі тим самим рядком, що й `--ner` (`spacy:` / `hf:` / `gliner:`, з опціями), мітки — як `--ner-label` (`LOC=АДРЕСА @pii`); таблиця «Сутності моделі» показує сирі мітки, щоб підібрати відповідність. У списку моделей — усі token-classification моделі акаунта [`davidmelash`](https://huggingface.co/davidmelash) (читається на старті Space; за замовчуванням `wechsel_base_v7_2026-10-09_r5_s43`), для них Space сам вмикає `trust_remote_code`; іншим репозиторіям ця опція заборонена. spaCy-модель з HF (`spacy:dchaplinsky/uk_ner_web_trf_13class`) завантажується як тека, без `.whl`. Логіка документа спільна з `run.py` (`run.annotate`), тож демо дає ту саму розмітку, що й CLI.

Локально: `pip install gradio spacy-transformers`, потім `python space/app.py`.

Автодеплой (`.github/workflows/deploy-space.yml`): після успішної **Evaluation** на push у main `.github/scripts/build_space.sh` збирає `space/*` і модулі пайплайну у `dist/space` і завантажує їх у Space (`hf upload`); Space створюється, якщо його ще немає. Ручний запуск: Actions → **Deploy Space** → Run workflow. Налаштування (Settings → Secrets and variables → Actions):

| Що | Тип | Значення |
|---|---|---|
| `HF_SPACE` | змінна | `<акаунт>/<назва>`; поки не задана, автодеплой пропускається |
| `HF_SPACE_TOKEN` | секрет | write-токен цього акаунта Hugging Face |
| `HF_SPACE_HARDWARE` | змінна, необов'язково | залізо нового Space, за замовчуванням `zero-a10g` (ZeroGPU) |

Gradio-Space на безкоштовному акаунті можливий лише на ZeroGPU і лише для акаунта, старшого за 30 днів; інакше потрібен PRO. Інференс іде на CPU, тож квоту ZeroGPU демо не витрачає. Що ще треба зробити, щоб запустити Space, і відомі ризики: [`space/NEXT_STEPS.md`](space/NEXT_STEPS.md).

## Як це працює

1. **ОСОБА.** Базово працює spaCy `uk_ner_web_trf_13class` (мітка PERS). Доповнює її regex: повне ПІБ (Прізвище Ім'я По-батькові), «Прізвище І. П.», «І. П. Прізвище», «Прізвище І.». Regex-фрагмент додається, лише якщо не перетинається з фрагментом моделі. Службові слова (позивач, відповідач, суд, головуючий…) відкидаються. Фрагменти однієї особи кластеризуються і отримують спільний номер (`ОСОБА_n`).
2. **НОМЕР, ІНФОРМАЦІЯ, АДРЕСА.** Правила в `predict_trf.py`; якщо NER-модель дає ці типи, її фрагменти йдуть додатковими кандидатами.
3. **Злиття.** Під час перетину кандидатів перемагає довший фрагмент. Особи від моделі мають пріоритет.

### Основні правила
- **АДРЕСА:** шаблон «[індекс] [область] [район] [місто] вулиця/проспект/… будинок [корпус] [квартира]» з відмінковими формами, складними назвами, хвостом (село, район, область, індекс) та варіантами без вулиці після тригерів «проживає / зареєстрований / за адресою». Адреси установ (суд, банк, прокуратура, ТОВ/АТ) відсіюються за контекстом.
- **НОМЕР:** телефони, IBAN, номери карток, паспорти (серія + 6 цифр) та ID-картки, ІПН/РНОКПП, VIN, номерні знаки, номери військових частин (в/ч), виконавчих проваджень («ВП № …») і машино-місць, 10-значні коди після «код / о/р / РНОКПП»; формати за стандартами плюс ключові слова поруч (ІПН, паспорт, телефон, ДНЗ…). Відкидаються номери в неособистому контексті (кадастрові, квитанції, номери записів і справ) та рахунки казначейства.
- **ІНФОРМАЦІЯ:** дати народження і смерті (за контекстом, не всі дати підряд, у т. ч. ISO; дата після «виданий» не вважається датою народження), email, нікнейми, соцмережі, військові формування (ТЦК та СП, навчальні центри…), державні органи у ролі сторони справи.

## Обмеження

- Правила АДРЕСА, ОСОБА й ІНФОРМАЦІЯ підбирались, зокрема, за аналізом помилок на тесті, тому оцінки трохи оптимістичні. Окремої розміченої валідації немає: train-вибірка містить лише сирі тексти.
- Найслабший тип — ІНФОРМАЦІЯ (P .69 / R .82). Розмітка маскує організації непослідовно, і правилами за формою цього не відрізнити. Далі ростиме дотренування трансформера на всі чотири класи або класифікатор «маскувати чи ні».
- «Військова частина А1234» у розмітці має тип НОМЕР, а не ІНФОРМАЦІЯ.
- Держоргани не маскуються: ст. 7 Закону «Про доступ до судових рішень» і п. 5 кодифікатора ДСА захищають лише фізичних осіб. Шаблон `STATE_BODY` у `predict_trf.py` знаходить родові назви органів і стандартні абревіатури, а кандидати ІНФОРМАЦІЯ, що з ними перетинаються (правила, модель, CRF), відкидаються. Офіційна розмітка маскує ті самі органи непослідовно, тому проти неї бал нижчий; проти `data/test/court_cases_fixed_state_bodies_open.jsonl` (виправлена розмітка без масок держорганів) вищий.
- Нові контекстні фільтри (`NUM_NEG`, `VP_NUM`, `ID10`) знайдено за помилками на тесті; на нових даних очікуваний приріст менший за виміряний.

## Потенційні рішення

Аналіз помилок режиму з CRF (до regex-виправлень): з 9,9 втрачених пунктів середнього ІНФОРМАЦІЯ забирає 6,3, АДРЕСА 1,8, НОМЕР 1,5, ОСОБА 0,3. Нижче те, що ще не реалізовано. «Виміряно» означає прогін на тесті з офіційним `evaluate.py`.

Усі 46 витоків осіб часткові: модель губить прізвище на початку документа (22, напр. «Павловський Олег Іванович» → «Олег Іванович»), по батькові (15) або ініціали (4). Частину втрат не прибрати жодним методом, бо розмітка сама собі суперечить (≈4,6 пункту середнього):
- ПІБ, розмічені як ІНФОРМАЦІЯ замість ОСОБА (10, напр. 116186753 «Соловйова Катерина Олександрівна»);
- «Військова частина А1234» як ІНФОРМАЦІЯ (4) проти НОМЕР (290);
- назви ТОВ/ПрАТ замасковано лише в 1 документі з 41;
- IBAN казначейства відкритий 14 разів і замаскований 1 раз;
- межі: АДРЕСА включає «по / на» перед собою 17 разів і не включає 29; НОМЕР включає «№ / в/ч» 12 разів і не включає 59. Це впливає лише на strict F1.
